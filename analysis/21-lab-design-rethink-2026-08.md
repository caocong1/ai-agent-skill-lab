# 本仓库设计重思 — 2026-08

> 分析版本：1.0 ｜ 最后更新：2026-08-23 ｜ 类型：**元层文件，不是来源分析** ｜ 依据：`analysis/01..20` 全量 + `.planning/freshness-reviews/2026-08-23-source-freshness-review.md`

这份文件回答一个和其他所有分析都不同的问题：**这个仓库自己的设计，在 2026-08 这个时间点还站得住吗？**

它不遵循来源分析的模板（没有"核心抽象/重要模式/适用场景"），因为它没有来源可分析——它的分析对象是本仓库。它也不替代 `analysis/07-overall-agent-analysis.md`：07 归纳的是"怎么做 agent"，本文追问的是"这套归纳该以什么形式存在、会不会过期、哪里已经错了"。

**先声明一处偏见风险。** `analysis/19-anthropic-harness-design-long-running-apps.md` 记录了一条明确的失败模式：让 agent 评估自己的产出时，它会自信地夸奖平庸的工作。本文正是**同一个 agent 评估自己参与构建的仓库**，处在那条失败模式的正中央。因此本文刻意做了三件事：把每条判断标注为"事实 / 推论 / 判断"，在末尾给出**可证伪条件**，并把"本仓库违反自己规则"的部分单独成节且写在前面而不是脚注里。读者应当把本文当作一份待复核的自评，不是结论。

## 一、本仓库的六条根基前提

先把隐含的东西显式化。这六条从未被完整写在一处，但它们是所有结构决策的实际依据：

| 编号 | 前提 | 体现在哪里 |
| --- | --- | --- |
| P1 | **从开源项目与权威文章中蒸馏出可复用 skill 是有价值的** | 整个仓库存在的理由 |
| P2 | **三层分离：`raw/` 证据 → `analysis/` 判断 → `skills/` 复用** | 目录结构；`iterate-skill-lab` 的模式划分 |
| P3 | **skill 是给 agent 读的 markdown，通过 router + progressive disclosure 加载** | `build-ai-agents` 从单体改为路由器 + 10 个 child skill |
| P4 | **SemVer 管契约，每来源独立分析版本** | `metadata.version`；SOURCE_INDEX 的双版本列 |
| P5 | **周期性新鲜度审查能防止内容腐坏** | SEED-001 + `.planning/freshness-reviews/` |
| P6 | **形态选择（workflow / loop / graph / harness）是首要决策轴** | `analysis/07` 的形态光谱；`design-ai-agent` 的入口问题 |

下面逐条压。

## 二、逐条压力测试

### P1 蒸馏有价值 —— 成立，但需要一个此前没有的判别式

**最强的反证**来自本轮新增的 `analysis/19`：*"harness 里的每一个组件，都编码了一条关于模型自己做不到什么的假设……随着模型进步，它们会很快过时。"* 一份 skill 就是一个 harness 组件。按这条逻辑，本仓库的产出有保质期，且保质期随模型进步而缩短。

同一篇文章给了具体证据（**事实**）：Sonnet 4.5 需要 context reset，Opus 4.5 让它被整个删除；Opus 4.6 让 sprint 这一构造被整个删除。`analysis/20` 给了协议层的同款证据：MCP 弃用 Roots / Sampling / Logging，三条理由分别是"server 现在能直接调 LLM API""tool 参数已经够用""生态补上了 OpenTelemetry"——**都不是被更好的设计取代，而是被周边能力变强淘汰的**。

但把这条推到"所以蒸馏没意义"是错的（**推论**）。被删掉的那些组件有一个共同特征：**它们补的是模型的能力缺口**。而同一轮证据里，另一类内容不但没有被淘汰，反而变重了：

- **权限与授权边界**：DeepSeek 的单调 guard（返回类型里根本没有 allow 结果，所以监听器顺序无法重新打开一个拒绝）、`ApprovalOutcome` 的闭合四元组、OpenAI Agents JS 在重放歧义时 fail-closed 且序列化凭据在恢复时一律不被信任。模型越强，它能做的事越多，**授权边界越重要而不是越不重要**。
- **完成判定归属**：模型越强，它作为自评者就越有说服力，**独立判定的价值随之上升**。三个互不相干的来源（DeepSeek goal domain / learn-claude-code s17 / Anthropic evaluator）在同一季度独立收敛到这条。
- **副作用治理**：模型能力不会让外部系统变成事务性的。Pi 的 effect sandwich、MCP MRTR 的幂等要求、LangChain4j 的补偿动作，解决的是分布式系统的老问题，与模型代际无关。
- **成本与前缀经济学**：能力不会让 token 变免费。MCP 把"确定性工具排序"写进规范并直接点名 prompt cache 命中率，是这条第一次进入协议层。

**判定**：P1 成立，但本仓库此前**没有区分这两类内容**，于是它们混在同一份 skill 里以同一种语气陈述。这是本次重思得到的**第一条新启发**，展开在第三节。

### P2 三层分离 —— 成立，但层边界在漏

**事实**：本轮新鲜度审查发现 **10 条失效路径**——`SOURCE_INDEX.md` 与 `source-map.md` 里引用的 `raw/repos/*` 内部文件，因为上游重命名（Pi 的 `agent-harness.md` → `harness.md`）或重编号（learn-claude-code 20 课 → 17 课）而不再存在。

这不是疏忽，是**结构问题**（**判断**）：`raw/repos/*` 是 gitlink，本仓库只记录 commit 不记录内容；而 `analysis/` 与 `skills/` 却引用了那一层内部的**裸路径**。裸路径在一个只存指针的层里是没有意义的——同一个路径在不同 commit 下指向不同的东西，或者不存在。P2 说"每层拥有自己的抽象层级、引用而不复制"，但引用的形式没有带上层归属所需的信息。

**处置**：本轮已修复所有失效路径，并把"逐条核对引用路径是否仍存在"写进新鲜度审查方法。更结构性的修法（把路径列表连同 commit 一起记，使其成为可解析的锚点）留待下轮。

### P3 router + progressive disclosure —— 成立，但缺一道机械闸

**事实**：`analysis/18` 记录了 DeepSeek Harness 的 Model Experience README 契约——每个包的 README 必须以 `## Model Experience` → `### <condition>` → `#### What the model sees` / `#### Token effect` / `#### KV Cache effect` 结尾，然后是 `## Known Limitations and Deferred Work`，**并且这个格式是被机械 gate 检查的**。同一份材料里，Agent Notes 的目录三态（proposed / implemented / rejected）与"提案期标题会被 gate 拒绝"也是机械检查的。

本仓库有同等严格的**约定**（分析文件的元数据 blockquote 格式、六个固定章节、SOURCE_INDEX 的双版本列、`docs/index.html` 的三 `<td>` 结构、版本号必须在四个文件里一致），但**没有一处是被检查的**。约定靠人（和 agent）每次记得，这在多轮迭代后必然漂移——本轮的 10 条失效路径就是漂移已经发生的证据。

**判定**：P3 的形式成立，但缺失的是 DeepSeek 那半边——**没有 gate 的契约不是契约，是习惯**。这是**第二条新启发**。

### P4 SemVer —— 不足，需要补弃用政策

**事实**：MCP 2026-07-28 采纳了三态特性生命周期（Active / Deprecated / Removed）+ **最短 12 个月弃用窗口** + 一份**集中的已弃用特性登记表**。

理由很清楚（`analysis/20`）：SemVer 只回答"这次是不是 breaking"，弃用登记表回答"**下次哪里会 breaking**"。前者让下游被动响应，后者让下游可以规划。

本仓库的 `build-ai-agents` 契约（被 SemVer 保护的 mode / deliverable / reference 三类）只有 MAJOR 规则，**没有弃用概念**。如果哪天要移除一个 child skill 或改一个 mode 名，当前流程只能直接 MAJOR，没有过渡期。

**判定**：P4 不完整。**第三条新启发**：对外契约需要"三态 + 最短窗口 + 登记表"，成本很低（一节文档），收益是让下游有规划空间。

### P5 周期性新鲜度审查 —— 成立，但触发集不完整

**事实**：本轮审查的实际触发是"快照超过一个季度"，但**真正的因**是 MCP 规范修订——它在三周内同时驱动了 MCP TS SDK 的 v2 包名重组、OpenAI Agents JS 的 v2 协商、LangChain4j 的 2026-07-28 客户端。一个上游规范修订，扇出到三个下游。

SEED-001 的触发集是"新里程碑 / 新增 provider-API 集成指导 / 快照超过一个季度"——**没有"上游规范修订"这一条**。更糟的是，MCP 规范此前在本仓库只以一条 Official Links 链接存在，**没有版本行**，因此它根本不在漂移检测的覆盖面内：2025-11-25 → 2026-07-28 这一跨越对本仓库是完全不可见的。

同时，seed 的 `scope: small` 估计在本轮失效（实际 medium）。这个估计对"平静季度"成立，对"规范修订季度"不成立。

**判定**：P5 的机制成立，输入面有洞。**处置**：规范类来源必须有 `来源版本` 行才能被覆盖（本轮已建行），"上游规范修订"应成为显式触发（已记入 seed）。

### P6 形态选择是首要轴 —— 仍然成立，但不再唯一

**事实**：形态光谱本轮从 13 档增加到 18 档（新增 Code Mode / 脚本编排 runtime / goal gate / 插件树 harness / 持久化执行 harness）。它还在正常增长，说明这个轴仍然有解释力。

但本轮的材料里，另一个轴反复出现，且**每次都是作为最重要的产物**被强调（**推论**）：

- DeepSeek 要求每个包写清 **"模型看到什么"**（What the model sees / Token effect / KV Cache effect），并把 `model-visible ⟺ logged` 立为不变量；
- learn-claude-code s15 的核心产出是一张**"组件在循环里的位置表"**——每个机制从哪个位点进入模型的可见面；
- MCP 2026-07-28 的全部重大变更都在改**模型与服务端之间那层可见面**（`_meta` 携带什么、`resultType` 是什么、结果里有没有 `serverInfo`）；
- learn-claude-code s17 推出的提示词义务是"把命令和结果明确写进对话"，因为**判定器只能看见对话**。

把这些放一起，浮现出的第二根轴是：**模型可见面 + 授权归属**——模型看得见什么，以及谁有权决定发生什么。这两件事**不是形态的推论**：同一个形态（比如 tool loop）可以有截然不同的可见面设计和授权设计，而这些差异恰恰是本轮所有安全与可靠性教训的所在地。

**判定**：P6 成立但应从"唯一首要轴"降为"第一入口问题"，与"可见面 + 授权"并列。**第四条新启发**。

## 三、一条新的组织轴：易腐 vs 耐久

这是本次重思最主要的产出。

把本仓库所有 skill 内容按"**它补的是什么**"重新分类，会得到两堆性质完全不同的东西：

| | **易腐类（compensation）** | **耐久类（governance）** |
| --- | --- | --- |
| 它补什么 | 模型当前做不到的事 | 授权、证据、副作用、成本——这些不因模型变强而消失 |
| 例子 | 上下文压缩策略、context reset、sprint 分解、防死循环的提示词补丁、为弱模型准备的分步引导 | 权限在执行边界、恢复时不继承授权、完成判定归属、幂等与补偿、prompt 前缀稳定性、成本预算 |
| 模型变强时 | **价值下降**，可能整块删除 | **价值上升**（模型能做的更多 ⇒ 边界更重要；自评更有说服力 ⇒ 独立判定更必要）|
| 应该怎么写 | 标注"针对哪一代模型的哪个缺口"，并附消融方法 | 按原则陈述，不绑定模型代际 |
| 复核节奏 | 每次模型代际更新时重扫，默认假设它已过期 | 随上游规范/生态变化更新，不随模型代际动 |

本仓库此前把这两类混在同一份 skill 里，用同一种语气陈述，读者（和执行 skill 的 agent）无从判断哪条该在换模型后重新验证。

**这条轴带来三个可操作的动作**（本轮落地）：

1. **易腐类条目要带日期与缺口说明**。形如"我们加 X，是因为模型在 M 版本做不到 Y"。模型升级时，这份清单就是消融清单。`analysis/17-mini-swe-agent.md` 已经给了消融方法，缺的是被消融对象的登记。
2. **耐久类条目要写成不带模型假设的原则**，并且在评审 skill 时优先保护。
3. **模型升级是一个显式的复核触发**，与"快照过期"并列写进 SEED-001 的触发集。

**这条轴同时解释了本仓库为什么还有存在价值**（**判断**）：如果本仓库的内容大部分是易腐类，那它会随模型进步趋近于零。而按上面的分类过一遍，本仓库沉淀最重、被最多来源交叉验证的那些条目——权限边界、完成判定、副作用治理、成本经济学——**全部落在耐久列**。易腐的那部分（压缩策略、上下文管理细节）确实在贬值，但它们本就不是本仓库的重心。

## 四、本仓库违反了自己的规则（三处）

这一节写在前面而不是脚注里，因为它是本文最不舒服也最有用的部分。

### 违反一：教了 gate，自己没有 gate

`skills/optimize-agent-skills/SKILL.md` 吸收 SkillOpt 的结论是明确的：skill / prompt / tool description 的修改**不是随手润色，而是行为变更**，应该有 baseline、验证集、拒绝记录和 staged adoption。

本仓库自己修改 skill 的方式是：读来源 → 判断 → 直接改 SKILL.md → 提交。**没有 baseline，没有验证集，没有一条拒绝记录**。本轮 2.2.0 改了 9 个 skill，其中每一条修改是否真的让下游 agent 表现更好，本仓库**不知道**，并且按当前流程**无法知道**。

诚实的补充：完整 SkillOpt 循环（rollout 真实任务 + held-out 验证）对一个单人维护的文档仓库是过重的。但"完全没有"和"完整 SkillOpt"之间有中间态——一组固定的评审场景，改动 skill 后跑一遍看结论是否还成立。这是下轮该做的事，本轮先把这条违反记录下来。

### 违反二：教了机械约束，自己只有约定

`analysis/14-openai-harness-engineering.md` 的结论之一是"反馈应该从说明升级到机械约束"；`analysis/18` 的 DeepSeek 把 README 格式与 Agent Notes 目录做成 gate。本仓库有一整套格式约定，**零机械检查**。本轮已把最小可检项做成脚本（见 `scripts/check-lab-invariants.sh`）——这是"从说明升级到机械约束"在本仓库自己身上的第一次落地。

### 违反三：教了非目标清单，自己没写

`analysis/01` 记录 Pi 明确列出不做的事，`analysis/20` 记录 MCP 明确删除流恢复，本文第二节把"非目标清单应与能力清单同等醒目"列为收敛结论。**本仓库自己没有非目标清单**：README 说了它是什么，从没说它不是什么。

补上（本轮落地到 README）：本仓库**不做**——不承诺 skill 内容与任何框架的当前版本 API 一致（只给核对纪律）、不做自动化来源摄取（判断是贵的那部分）、不发布为可安装包、不为多语言维护平行译本、不充当上游文档的镜像。

## 五、不该改的东西

重思的另一半是识别**没坏的东西**，避免为了显得有产出而churn：

- **三层分离本身**（P2 的结构，不是它的引用形式）：本轮新增三个来源全部顺利走完 raw → analysis → skills，管道有效。
- **中文分析 + 英文 skill 的分工**：分析是维护者的思考空间，skill 是给下游 agent 读的执行契约，两者读者不同，语言分工合理。没有证据表明需要统一。
- **router + child skill 的拆分**：progressive disclosure 在 skill 层的应用，与来源（Pi 的 skill catalog、DeepSeek 的 agent scope）一致。是否 11 个是最优数量**无法在没有 eval 的情况下回答**——这正好又指回违反一，不应靠感觉调整。
- **一步一 commit + 草稿 PR 的流程**：可审计、可回退，与 `analysis/19` 的"保留每次迭代产物并可回退"一致。
- **gitlink 而非 vendor 拷贝**：避免了版权与体积问题，代价是路径易腐——而路径易腐已有更便宜的解法（核对 + 带 commit 的引用），不值得为它改变存储模型。

**下轮该做：**

## 七、可证伪条件

本文若干判断是可以被证伪的。写下来，以便下次审查时能反过来查自己：

1. **如果**下一次模型代际更新后，按"易腐"标注的条目里**没有任何一条**需要删除或修改，那么易腐/耐久这条轴是无用的分类（它没有预测力），应当撤回。
2. **如果**机械闸脚本在此后三轮迭代里**从未拦下任何一次违规**，说明本仓库的约定漂移问题被高估了，脚本应当删除而不是继续维护。
