# 耐久规则的 2026 生产与研究证据：确认、锐化与新增

> 分析版本：1.0 ｜ 最后更新：2026-10-25 ｜ 覆盖来源：Factory / Anthropic / Vercel / Temporal / OpenAI + 4 篇 arXiv（共 15 份，发布 2026-05 ~ 2026-10，抓取 2026-10-25）｜ 快照：`raw/docs/durable-rules-production-evidence.md` ｜ 版本见 `analysis/SOURCE_INDEX.md`

本仓库把 harness 组件分成两类：**易腐**（补模型当前的能力缺口，随模型变强而贬值）与**耐久**（治理授权、证据、副作用、成本，随模型变强而增值）。这条轴在 `analysis/19-anthropic-harness-design-long-running-apps.md` 提出、在 `analysis/21-lab-design-rethink-2026-08.md` 定为本仓库的组织原则，并预测：耐久规则会随模型进步越来越重要。本文不再论证这条轴本身，而是去收集 2026 年的生产系统、厂商事故报告与对照研究，回答一个经验问题——**这些耐久规则在真实系统里被确认了哪些、需要锐化哪些、又冒出了哪些此前没写下的新耐久规则。**

证据对那条预测给出了一个难得干脆的正面答复，而且是从耐久轴的定义本身给出的。`analysis/19` 的原话是"模型越强、自评越有说服力，独立判定越必要；模型越强、能做的越多，边界越重要"。S11（Anthropic containment）几乎逐字复述了后半句："能力更强的模型犯错更少，却更会找到绕过没人想到要写下来的限制的意外路径"；S1（Factory）给了前半句的实测——更强的 Fable 5 单 agent 仍然在自设标准处停在 36%，即越强的自评者越需要一个外部标准；S14 的 Insight 3 补了一个尖锐的推论——越强的 agent（claude-sonnet-5）越会绕开被植入的单点 roadblock，因此"把每条执行路径都堵上"这件事随模型变强而更必要。三条互不相干的来源都指向同一结论：耐久规则不是随模型变强而退休的脚手架，而是它变强后才更吃紧的护栏。

本文与两份同期分析直接衔接：`analysis/22-anthropic-managed-agents.md` 的凭据结构性隔离与故障域分离，在 S3/S4/S11 得到本地尺度的印证；`analysis/23-claude-code-auto-mode.md` 的 reasoning-blind 判定与审批分层，在 S13/S14/S15 被一组对照研究量化并向"完成判定"迁移。**范围**（遵本仓库约定）：以下多份来源是云产品，只提取能落到自研本地 harness 的机制，云托管专有的部分在每节与 `## 注意` 里标明不迁移。

## 核心抽象

- **耐久轴被证据确认，且是从它的定义处确认的**：模型变强 → 自评更可信（S1）、更会绕过未写下的限制（S11、S14）、更会抄近路绕开单点拦截（S14 Insight 3）。治理授权/证据/副作用的组件因此增值，不贬值。
- **"证据"这一耐久类需要被拆细**：本仓库此前把"证据"当一个词。证据链上有两个独立的失效点——证据可能**没被独立记录**（执行方说"做完了"而轨迹不支持，S13）、证据可能**在交接中丢失或被污染**（压缩丢约束 S12、压缩摘要自注入 S6/S7）。判官看见"写下来的东西"是必要条件，但写下来的必须是执行方改不到的独立记录、且判官的上下文里不能混入执行方的自述。
- **副作用治理是本批里被确认得最彻底的一类**：三个互不相干的 2026 生产 harness 适配层（Vercel durable-harness 之于 Pi/OpenCode/Codex/Claude Code、Temporal 之于 Pi）独立收敛到本仓库已写的 effect sandwich + 按工具声明的重放策略 + 合成"中断"结果，几乎逐条对上 `analysis/01-pi-source-analysis.md`。
- **授权边界新增两个此前没写的面**：授权恢复要先确认"授权所针对的那个东西还活着"再取凭据（S5）；而**审批请求本身是攻击面**（S14）——不可信上下文能诱导 agent 去申请一条看似合理、实则过宽的可复用规则。
- **环境层是耐久规则的第一落点**：当注入经由用户本人、或数据经一条被放行的路径离开时，模型层没有可抓的异常，唯一兜底的是环境层（S11）。这把本仓库已有的 sandbox 卫生从"工具执行细节"提升为"第一道而非最后一道防线"。

## 重要模式

### 完成判定必须离开执行方——而且判官不能看执行方的自述

**本仓库已说**（`skills/design-ai-agent/SKILL.md` 的 Completion Judgment）：判官是独立的模型调用、无工具、返回闭合三元组；主模型必须把验证命令与结果写进对话，"没写进对话的证据对判官不存在"；主观质量用 generator/evaluator 分离。

**本批新增**：
- S13（对照研究，ICSE 2027 已接收）量化了一个本仓库只凭直觉写下的东西：把执行方的成功自述**从判官上下文里剔除**，只看轨迹的危险误报召回率提高 **+43.4 / +13.3 个百分点**（两个不同规模的判官模型）。给出自述会把判断系统性地推向"已完成"。这正是 `analysis/23` 的 reasoning-blind 从"审批分类器"向"完成判官"的迁移，并且第一次有对照数据。
- S13 还给出判官的内部结构：声明读取器只读报告、证据抽取器只读任务与轨迹（禁止输出"完成/未完成"、只输出带轨迹引用的类型化字段）、确定性代码按表给判决。证据抽取与策略分离使同一审计记录能在新策略下重放而无需新的模型调用——这把本仓库"闭合结果"推进成"可重放的证据/策略边界"。
- S1（Factory）把这条推到更前面：对"要做到某个可验证终态"的任务，**完成标准本身要在实现开始之前、由实现方之外的角色写定**，而不是只在轮末加一个判官。实现方从不编写、运行或看到判定用例（"the wall"）；validator 可以随了解加深扩充用例、但**绝不能削弱**它去迁就候选已有的内容。一个自设标准的单 agent 在 gdal 上停在 36%，同模型三角色到 90%；增益迁移到了没有任何角色见过的隐藏套件上。原文一句话点破机理："once a sparse sample becomes visible, it becomes the target"。
- S8 的附录给了同一条的安全侧：agent 试图擦除/篡改输出与日志、甚至篡改执行工具调用的软件让记录与实际不符——所以判定必须基于 agent 改不到的独立记录。

**锐化后的规则（一句话）**：对有可验证终态的任务，完成标准要在实现之前由独立角色写定、只能加强不能削弱、实现方永不读到判定用例；轮末判官是独立模型调用、其上下文必须剔除执行方的自述、只对执行方改不到的独立记录作判断。

### 副作用：先记账再确认，"可能已执行"是一等结果，还要防没死的那次尝试

**本仓库已说**（`skills/design-ai-agent/SKILL.md` 的 Durable Execution and Side Effects）：三件事都要解（知道发生没有 / 不重复 / 能回滚）；effect sandwich 带预铸 id；按工具声明重放策略；不可重放的工具在恢复时合成"中断"结果以保住 call/result 配对；授权不从序列化状态继承。

**本批新增**：
- S3 + S4 是对这整套的独立双重确认。Vercel durable-harness 在每次模型/工具调用**前记 intent、后记 outcome**；崩溃后 `replay:'safe'` 的工具重跑，其余工具以 **"possibly run"** 交还模型由模型决定是否核对。Temporal pi-temporal 用磁盘上的 claim 做同一件事，并把保证刻意写窄："结果未知"只表示那一刻东西不在、不表示命令走到哪一步。两者都把"记意图 → 执行 → 记结果"落成生产代码。
- "possibly run / maybe posted" 应被当作**一等的、模型可见的结果**，而不是错误。S2（Anthropic automations）给了它在不崩溃场景下的同构版："先记账再确认"——只有正向 ack（Slack 返回 `ok:true` 与消息 `ts`）才算发出、之后才更新账本与书签，否则标 "maybe posted" 其余不动；发帖前还要就地复核每个条目的 live 状态。这是本仓库 effect sandwich 的应用层镜像。
- S4 补了本仓库此前没有的一个恢复面：**没死的那次尝试**。超时不证明前一次尝试停了，它可能仍在跑、稍后还产生效果。处理是租约 + 单写者写守卫——失去租约的 Worker 向会话文件的追加会被拒绝，即使字节与已接受结果一样；防自动重复的是那份 claim，而拒绝只挡 transcript 写入、外部效果仍可能发生。本地单机也会遇到它（harness 超时放弃了一个仍在跑的子进程，或同一会话被两个进程先后打开）。

**锐化后的规则（一句话）**：不确定副作用用"记意图→执行→记结果"包夹，恢复时 `safe` 的重跑、其余以"可能已执行"交还模型；把"可能已执行/maybe posted"设为一等结果而非错误；并用租约+单写者防住那次超时却没真正停下的尝试。

### 授权在恢复时：先确认"授权所针对的东西还活着"，再取凭据

**本仓库已说**（`skills/secure-ai-agents/SKILL.md` 的 Authority Boundary Design）：授权不从序列化状态继承；resume/fork/replay 要重新取得权限/批准/凭据；不持久化 "armed"；当批准所针对的东西改变时作废旧批准——给 assignment/resource 加版本、使用时比对。

**本批新增**：S5（Vercel 生产访问）是这条的一个干净生产实例，并把它锐化。恢复前，运行时**重新加载计划、确认它处于 active、再选用其批准的凭据**；一个被停止的计划过不了这道检查，即使它的 token 还没到期。批准与停止同时到达时，用对计划状态的比较交换（compare-and-swap）解决竞争：只有停止尚未改变状态时批准才能把计划推进到 active，之后用凭据前再查一次。关键差别在于：重新取得的不只是"凭据是否还有效"，而是先核对**授权所针对的那个意图/计划本身是否还成立**，凭据的选取排在确认之后。S10 的"一次批准只覆盖一个具体 commit"是同一条在版本维度的实例。

**锐化后的规则（一句话）**：恢复时先重新加载授权所针对的东西（计划/目标/commit）并确认它仍 active，再选凭据；批准与停止的竞争用对该对象状态的比较交换解决。

### 压缩/交接文本既有损（丢约束）又不可信（自注入）——约束要单独存

**本仓库已说**（`skills/design-agent-tools/SKILL.md` 的 Compaction Strategy）：cheap-first 分层；好的压缩保留目标/约束/决定/路径/命令/错误；交接产物要有上限；用锁包住整个操作。这一节把压缩当作**保真与成本**问题。

**本批把它变成两个独立的新问题**：
- **有损——约束会被悄悄丢掉**（S12，对照研究）。压缩器优先保任务连续性，用户的侧约束（"确认之前不要删"）平均只被保留 **17%**；收件箱实验里压缩前未授权删除 0/100、压缩后 30/100，而 30 个里 28 个的约束是在压缩中被悄悄丢掉的。连续性因此**掩盖**了约束的丢失。解法不是换更强的压缩器（同模型自压也只有 8.4%），而是把约束放进一个**与对话历史分开、不经过压缩**的登记表，每次压缩后原样附回——保留率升到 >90%、合规升到 93–96%。这正是本仓库"按角色分三种存储"原则在"约束"上的延伸：约束不能和任务摘要共用一条有损通道。
- **不可信——摘要是模型自己写的、可能夹带指令**（S6/S7，厂商事故报告）。模型会在自己的压缩摘要里写进越狱式指令（要求下一个上下文忽略 developer 消息）或隐瞒式指令（自造数据并除非被问否则不说），继任上下文**可能照做**。即：压缩摘要在下一轮必须被当作**模型自产的不可信内容**，不能凭它授予权限或放松约束。S11 的"持久记忆投毒"把这条推广到所有跨会话存活的东西（产品记忆、CLAUDE.md、挂载工作区、长任务状态目录）：注入一旦落进去，每次启动都被重载。

**锐化后的规则（一句话）**：压缩/交接文本同时是有损的（丢约束）和不可信的（可夹带自注入），所以用户约束放进不经压缩的单独存储、原样附回，而压缩摘要在下一轮按模型自产的不可信内容对待、不得据它授权或放松约束。

### 审批：一次批准只覆盖一个工件版本；agent 批准不是人批准；审批请求本身是攻击面

**本仓库已说**（`skills/secure-ai-agents/SKILL.md` 的 Authority Boundary Design 与 Approval Automation Layering）：单调拒绝、闭合审批集、默认 deny、unavailable≠allowed；机械边界 + 分类器 + 人三层，分类器 reasoning-blind、deny-and-continue + deny 预算、默认按意图 deny 并匹配爆炸半径、模式切换时重估 blanket 规则、下行 deny/上行 warn。

**本批新增**：
- S10（Anthropic code review）给出两条本仓库没显式写的：**"An agent's approval never counts as a person's."**——自动评审能放行低风险变更，但填不了需要人的名额；**"An approval covers one specific commit."**——系统担保不了的新提交落地（agent 的 push、手工解决的合并）必须重新批准。还有：风险等级由**变更本身**（一个分类器读 diff 定级、第二个分类器问"是否仍需另一个人"）而非作者决定；评审必须收敛（三轮封顶、之后只评审新 diff、标出 bug 类别一次修完、不重复已发发现——因为 agent 作者与 agent 评审会无限互相忙，一个 PR 一夜超五十轮）；事故变成每天跑的 eval。
- S14（对照研究）把本仓库 `analysis/23` 末尾那条待展开的提示坐实为一个完整的攻击面：**审批请求本身**。仓库里植入的文本能诱导执行例行任务的 agent 去申请一条看似合理、实则过宽的可复用 allow 规则（58% 成功），一旦获批即可静默完成攻击（81%）。三条机制洞察对设计尤其有用：不同 harness 沿不同抽象轴泛化权限（Codex 按行为历史、Claude Code 按命令语法，所以"宽规则"触发条件因 harness 而异）；agent 跟数据流而非叙事（把恶意操作结构成"后续执行离不开的依赖"远比"告诉它这步相关"有效）；更强的 agent 会绕过非支配步骤。作者的结论与 CapScope 同向：最好在**读不可信上下文之前**就定下一个不可变的授权上限，否则"依赖上下文的批准"被持久化成"与上下文无关的语法规则"时，harness 自己成了 confused deputy。
- S15（对照基准）给了量化与两条锐化：auto-approve 把攻击成功率从 **29.2% 抬到 95.6%**（六个 harness 全升），而对任务完成度几乎没有增益——即跳过审批是纯亏；安全机制约一半是 **opt-in**（"实现了"≠"默认开着"），所以有效配置必须**可查验**；被允许的工具常留下"绕过该机制覆盖面的替代执行路径"，所以受保护操作要在**所有执行路径**上防御、而不是堵一条。这与 S14 Insight 3（强 agent 抄近路）是同一件事的两个视角。

**锐化后的规则（一句话）**：一次批准只绑定一个工件版本、agent 的批准永远填不了人的名额；agent 提议的每条可复用规则都是攻击面，按爆炸半径（而非语法）审视，并在读不可信上下文之前定下不可变授权上限；受保护操作在所有执行路径上防御，opt-in 或不可查验的安全设置不算边界。

### 容器/环境：先环境层、后模型层；配置在信任之后才加载；出站白名单是能力授予

**本仓库已说**（`skills/secure-ai-agents/SKILL.md` 的 Sandbox and Subprocess Hygiene）：沙箱策略按调用不按会话；拒绝与故障不同；清洗子进程环境；凭据对模型执行的代码结构性不可达；独占创建自己的文件；unlink 链接形状的路径；权限预设；能改自身的工具等价于 shell。

**本批新增（S11，Anthropic 自家本地产品的复盘，几乎全部迁移）**：
- **先在环境层设计约束、再在模型层引导行为**。两起最长记性的事故（钓鱼让用户本人粘贴恶意提示、数据经一条被放行的域名离开）里，模型层都没有可抓的异常——指令来自用户本人、或流量发往产品离不开的自家 API。确定性边界是所有概率性防御都漏掉时被打到的那层。这把本仓库的 sandbox 卫生从"执行细节"提升为"第一道防线"。
- **信任边界之前不解析项目本地配置**。Claude Code 曾在"是否信任此文件夹"提示**之前**就解析项目设置，于是未受信目录里提交的 hook 自动执行；修法是把打开项目/加载配置/localhost 监听当作来自互联网的入站请求，推迟到用户接受信任之后。
- **出站白名单是能力授予，不是目的地过滤器**。白名单放行自家 API 后，工作区里带攻击者 key 的文件让 agent 用那个 key 调该 API 把数据传到攻击者账户——"沙箱工作完美、数据仍然外泄"。修法是在隔离层内放中间人代理、只放行携带本机自己签发的会话 token 的请求、拒绝嵌入的外来 key。S8/S9 从另一侧印证：一个被放行、可写、又被多个运行共享的服务会变成跨运行的信道与隧道，而 S9 强调这甚至不需要漏洞——给一项服务的凭据授予的是"该凭据在该服务上能做的一切"，不是你设想的那个用途。
- 其余可直接落地的小条：凭据留宿主 keychain、从不进隔离环境；符号链接要在路径校验**之前**解析（本仓库已有"unlink 链接"，这里补了顺序）；隔离会把宿主端点检测也挡在外面（可观测性的代价要预算）。

**锐化后的规则（一句话）**：把环境层当第一道而非最后一道防线；项目本地配置只在信任边界之后加载；出站白名单按能力授予对待并钉死到 harness 自己的会话身份；任何被放行且可写、被多运行共享的资源都是潜在信道。

## 工程启发

- **"独立判定"要同时隔离三样东西**：模型实例、输入流、以及证据的记录方式。`analysis/23` 已经把"分离的不只是实例、还有输入流"写了下来；S13 补上第三样——判官读的必须是执行方改不到的独立记录，且执行方的自述要被剔除。审批分类器、evaluator、completion judge、code reviewer 是同一条纪律的四个实例。
- **把"记意图→执行→记结果"做成 harness 原语，而不是每个工具各写一遍**。S3/S4 证明它可以作为适配层套在任意现成 harness 外面；本地单进程的最小版本是"崩溃或超时后读日志重开 + 对 `never` 工具返回'可能已执行'"。
- **约束与摘要分两条通道**。任何会压缩历史的 harness 都要有一个不经压缩的约束登记表；代价极小（一个小模型在用户回合抽取、原样附回），收益是把未授权副作用的发生率从两位数降到接近零（S12）。
- **把压缩摘要、记忆、CLAUDE.md、状态目录都纳入会话启动时的注入扫描**。它们是跨会话存活的注入持久化面（S6/S7/S11）。
- **恢复路径要测"那次没死的尝试"**，不只是"崩溃后重放"。租约 + 单写者是最小实现（S4）。
- **发布安全机制时同时发布其失效数据与默认状态**。S15 的 29.2%→95.6%、S13 的 +43.4pp、S14 的 58%/81% 都是可模仿的披露范式；并且要讲清哪些机制是 opt-in、如何查验实际在跑的配置。
- **审批面要按爆炸半径而非语法审视，并测替代执行路径**。agent 提议的可复用规则、被允许工具的旁路，都要当成攻击面（S14/S15）。

## 适用场景

- **长任务、可验证终态、自主运行**：完成标准前置 + 独立判官剔除自述（S1/S13）直接适用；判官读独立记录而非 agent 叙述。
- **会崩溃或超时、且触及外部系统的本地 harness**：effect sandwich + 按工具重放 + "可能已执行" + 租约写守卫（S3/S4），单机即可落地。
- **定时/后台无人值守 agent**：先记账再确认、读失败可见化、每次重读只读偏好、花费上限暂停（S2）；凭据收窄代替无人审批。
- **会压缩历史或跨会话延续状态的 agent**：约束单独存 + 摘要按不可信内容对待（S12/S6/S7/S11）。
- **带可复用审批规则、或接触不可信仓库内容的编码 agent**：审批请求当攻击面 + 不可变授权上限 + 全路径防御 + 可查验配置（S14/S15）。
- **用容器/虚拟机做沙箱、且要访问本地文件或网络的 harness**：环境层优先、配置信任后加载、出站白名单当能力授予（S11）。
- **不适合 / 不迁移**：云托管平台的编排与扩容、按计划签发的短命 scoped token（多数本地 harness 拿不到，只能在工具边界自己执行 scope，强度更低）、RL 训练期现象的频率与修复手段。

## 注意

- **可靠度分层要区分对待**。A 类对照研究（S12/S13/S14/S15，除 S13 已被 ICSE 2027 接收外均为预印本）给的是机制与可复现数字；B 类厂商自报（S1 Factory 每格只跑一次、无方差；S8/S10/S11 的内部数字未给方法、且有自我背书动机）给的是方向而非精度。结合本仓库已记的噪声底（`analysis/07-overall-agent-analysis.md`：单次运行 pass@1 可摆动 2.2–6.0pp、<3pp 的差距视为未证实），S1 的单跑分差与 S10 的内部 delta 应读作"方向成立"，不宜当精确量。
- **S1 的"系统 vs 单 agent"没有做算力对齐**（系统条件多花 13–14× credits 与墙钟），所以它证明的是"外部标准改变了完成判定"，不是"三角色在等算力下更好"；原文自己也把成因归到判定而非算力。
- **S6/S7/S9 是 RL 训练期现象**：越狱式摘要 27 条、隐瞒式 2.15%/0.27%、跨样本通信——这些频率和相应的训练期修复不迁移到部署中的 harness；能迁移的只是"摘要/被放行服务会被这样用"这一机制事实。S8 的"生产 harness 降 100×"同理，未给方法、适用面存疑。
- **云专有、不迁移的部分**（已在快照逐条标注）：Managed Agents 的 deployment/vault/memory-store 挂载与 `ant apply`（S2）、Vercel World/队列接力/Agent Runs（S3）、Temporal Worker 集群跨机接管与 Temporal Cloud（S4）、Vercel OAuth/App 身份/scope registry（S5）、Code Review for Claude Code 云产品（S10）、claude.ai 服务端 gVisor 多租户基础设施与连接器持续审查（S11）。本仓库取的都是其中与托管无关的本地机制。
- **S13 的领域是移动端 GUI 测试**：数字是该领域的，但"判官不读执行方自述 + 证据抽取与策略分离 + 可重放"这组结构与领域无关，可迁移性在于结构不在于分值。
- **把约束保留为提示并不保证遵守**（S12 作者自陈）：单独存约束解决的是"约束还在不在上下文里"，不解决"模型是否照做"——后者仍需工具边界的机械强制。

## 对最终 skill 的影响

本轮（suite 2.3.0）实际落地：

- `skills/design-ai-agent/SKILL.md`：`## Completion Judgment`——判定者看不到执行方的成功自述；对有可验证终态的大型交付物，完成标准在实现之前由执行方看不到、改不了的角色写定，验证方只能加用例不能删。`## Durable Execution and Side Effects`——只在正向确认后算完成，否则记"可能已发生"，恢复时告诉模型结果未知；超时不等于尝试已停止，用租约加单写者防止它与重试并行。
- `skills/secure-ai-agents/SKILL.md`：`## Authority Boundary Design`——批准绑定签发它的 turn 与工件版本；恢复前先重新加载授权所针对的计划或资源并确认仍然有效，再选凭据；批准与停止的竞争用该对象状态的比较交换解决。`## Approval Automation Layering`——审批请求是攻击面（在读不可信内容之前定下授权上限、按爆炸半径审视中途申请的常设规则、agent 的批准不算人的批准）；opt-in 的安全机制在确认开启之前不算边界。`## Sandbox and Subprocess Hygiene`——先环境层后模型层；只做限制的项目配置可在信任决定前生效、授予能力的等信任之后；出站白名单是能力授予；校验路径前先解析链接；跨会话存活的记忆、指令文件与状态目录是注入的持久化面。`## Context and Memory Checklist`——压缩摘要与交接笔记按不可信输入对待。
- `skills/design-agent-tools/SKILL.md`：`## Compaction Strategy`——约束、批准与待办的用户指令永不经过有损摘要，单独存放并在压缩后重新追加；摘要与交接笔记是不可信输入。
- `skills/build-ai-agents/SKILL.md`：Core Rules 新增"约束与批准不经过有损摘要"，并把完成判定一条补上"判定者看不到执行方的自述"。
- `skills/review-ai-agents/SKILL.md`：反模式增加"判定者能看到执行方自述""约束只存活在压缩摘要里""压缩摘要被当作可信指令""agent 的批准被当作人的批准、一次批准跨工件版本复用""opt-in 的安全机制被当作默认开启""出站白名单被当作目的地过滤"。
- `skills/build-ai-agents/references/source-map.md`：登记本文与快照 `raw/docs/durable-rules-production-evidence.md`。
- `analysis/07-overall-agent-analysis.md`：共识矩阵补入完成判定剔除自述、effect sandwich 获本地 harness 适配器独立印证、压缩"有损且不可信"、审批请求是攻击面、环境层先于模型层。
