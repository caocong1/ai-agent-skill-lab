## 文章背景

OpenAI 团队用 Codex 从空仓库构建并交付一个真实使用的软件产品，刻意要求产品代码、测试、CI、文档、可观测性和内部工具均由 agent 生成。文章关注的不是模型基准，而是当工程团队主要负责描述意图、设计环境和构造反馈闭环时，哪些系统能力会成为瓶颈。

## Harness engineering 的工作面

- 失败不默认归因于“模型不够努力”，而应检查 agent 缺少哪种可见、可执行、可验证的能力。
- 人负责目标、优先级、验收标准和少量高价值判断；agent 负责实现、测试、review、处理反馈与提交变更。
- 标准开发工具、仓库内脚本和 skills 直接暴露给 agent，减少人工在终端与聊天窗口之间搬运上下文。

## Agent legibility

- 应用不仅要能运行，还要能被 agent 观察：每个 worktree 可独立启动应用，并给 agent 提供浏览器控制、DOM/截图、日志、指标和 trace 查询能力。
- 独立 worktree 的应用、日志和指标共同构成任务级隔离环境，使 agent 可以复现问题、验证 UI、检查性能指标并在任务结束时销毁环境。
- 对 agent 不可访问的信息在执行时近似不存在。团队决策若只留在聊天、外部文档或个人记忆中，就无法稳定影响后续运行。

## Repository as system of record

- 简短 `AGENTS.md` 应是目录和导航入口，而不是巨型百科全书；详细知识放在结构化、可索引、带所有权与验证状态的 `docs/` 中。
- 架构、设计决策、产品规格、执行计划、技术债和生成的 schema 都应版本化并与代码共置。
- 渐进式披露优于把所有规则一次注入上下文：先给稳定地图，再让 agent 按任务读取更深的权威文件。
- 文档知识库本身需要 lint、交叉链接、freshness 检查和周期性 gardening，防止“看起来权威但已过期”。

## 约束、反馈与自治

- 文档用于说明意图，机械检查用于保证不变量。架构依赖方向、边界数据解析、结构化日志、命名和文件规模等规则适合编码进 lint 与结构测试。
- 约束应集中在边界、正确性和可复现性；边界以内允许 agent 自主选择实现。
- lint 错误也是 agent-facing interface：应携带可执行的修复提示，而不只是给人看的失败码。
- 人类反馈要被“编译”回系统：重复 review 意见升级为文档规则、lint、测试、skill 或工具能力，使同一判断以后自动复用。
- 随着复现、实现、验证、review、CI 修复和反馈处理被编码进 harness，单次 agent 运行可以覆盖更长的端到端生命周期；但这种自治依赖特定仓库投资，不能直接外推。

## 吞吐与熵

- agent 吞吐远高于人类注意力时，传统等待和重型人工 gate 的成本结构会变化；文章描述了短生命周期 PR 与快速后续修正的实践，但明确依赖其高吞吐、强隔离和真实产品反馈环境。
- agent 会复制仓库里已有的好坏模式，因此生成速度越快，架构漂移与重复坏模式传播也越快。
- 团队把“golden principles”编码成机械规则，并让后台 agent 持续扫描偏差、更新质量评分和发起小型重构，形成类似垃圾回收的维护闭环。

## 适用边界

- 文章是单团队、单产品、特定 Codex 环境下的经验报告，不是受控基准。
- “更少阻塞 gate”不是通用建议；低吞吐、高合规、高不可逆风险或隔离薄弱的系统仍需严格 gate。
- 百万行代码、PR 数量和时间节省属于作者团队的经验指标，应作为背景而非可复制承诺。
